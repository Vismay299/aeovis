## The two-controller collision — read before dispatching anything

Partway through this session, a **second** rebuild-controller was dispatched
believing the first had finished (it had returned `status: completed` after
dispatching its wave). It had not finished: **a background agent that
dispatched children appears to get re-invoked each time one of those children
completes** — not just the top-level session that spawned it. Evidence, in
order:

1. Commit `6eb350f` landed at 08:56:34 IST from the second controller.
2. Commit `b2e1cfb` landed 16 seconds later, authored in the first
   controller's voice, aggregating twelve tasks' work the second controller
   had never seen.
3. `tasks.json` was rewritten again at 08:57:42 with three new follow-up
   tasks stamped `"by": "controller"`.
4. No git hook, no `.claude/settings.json` hook — `git reflog` shows two
   ordinary commits 16 seconds apart from two live processes.

The second controller **caught this itself**, stopped before dispatching
anything, made one narrow docs-only commit that verifiably composed cleanly
(`.env.example`, the one file two already-submitted tasks both touched), and
surfaced the finding instead of guessing. Nothing was lost. That is the
correct behavior if this happens again.

**The rule going forward:** before dispatching a `rebuild-controller`, check
for live worktrees (`git worktree list`) and recent commits in the last few
minutes (`git log --oneline -5`). If either suggests something is already
running, **wait and re-check** rather than dispatching a second one. If you
must be certain, ask the operator whether a controller is known to be running
before starting one — this is exactly the kind of ambiguous state where a
question costs a message and a wrong guess costs a corrupted ledger.

## Locked decisions from this session, additive to the 2026-08-30 handoff

- **Verifiers run concurrently in isolated git worktrees, not serially.**
  The original one-at-a-time rule existed because verifiers sabotage source
  to prove a test bites, and concurrent verifiers in a shared tree see each
  other's sabotage. Isolated worktrees remove the shared state entirely —
  each verifier reads/mutates/restores its own copy — so running them
  concurrently is not just faster, it's safer: nothing to collide on. This
  was proven out across roughly 40 verifications this session with mutually
  consistent verdicts.
- **A verifier's own local scratch files can collide.** The per-session
  scratchpad directory is shared across every concurrently-running agent, not
  per-agent. At least one agent had a scratch file overwritten mid-run by a
  sibling. Worth a unique-prefix convention (e.g. the task id) before someone
  loses a measurement they can't re-run. Not yet fixed.
- **The LLM gateway is genuinely OpenRouter now**, not MiMo — this was fixed
  in an earlier session (see `docs/vendors/gateway-catalog.md` for the full
  incident writeup). `R5.1.3` remains blocked only on the operator supplying
  a real key; the config-side work is done.

## How the orchestration works (unchanged from 2026-08-30)

One controller dispatches implementer/test-author/verifier/surveyor/scribe
sub-agents. `orchestrate.mjs` is the only writer of `tasks.json` and enforces:

1. A task cannot close without a passing verification from an agent that did
   not write the code.
2. A close must carry a `file:line` citation that resolves.

```
status | next | show | claim | submit | verify | block | unblock
add | rule | amend | depend | render | validate
```

Run `validate` before every commit. `render` regenerates the human tracker
from the ledger, so it cannot drift.
